Permissions Handshake (HERMES_UID / HERMES_GID): When starting with make up, your host user ID and group ID are passed automatically into the container. This ensures all files created by Hermes inside /opt/data remain readable and writable by your normal user on macOS/Linux.

Data Flow Across the Four Services

Hermes does not talk to model providers directly in this stack. It talks to OmniRoute for inference and to Hindsight for long-term memory, and serves its own Web UI on port 9119. Hindsight in turn needs its own LLM to extract entities and synthesise reflections — and that is pointed back at OmniRoute as well.

Request paths inside the hermes-net bridge network

   you ──► make chat ─┤  hermes  (hermes-agent)      │
                      │  + Web UI :9119 (s6)        │

         inference        │                  │   long-term memory
         /v1/chat/completions                │   /v1/default/banks/...

              └─────────┬─────────┘   │ embedded PostgreSQL +   │

                        ▼             └─────────────────────────┘

Figure 1.2: One credential, configured once in the OmniRoute dashboard, powers inference and Hindsight's entity extraction. Embeddings and reranking run locally inside the Hindsight container and never leave your machine.
Service names, not localhost. Inside the Docker network the containers address each other by compose service name: http://omniroute:20128/v1 and http://hindsight:8888. localhost inside a container means that container. This is the single most common mistake when hand-editing config.yaml or ./data/hindsight/config.json.
Two volumes are deliberately NOT bind mounts. hermes-installs (at /opt/data/installs) and hindsight-pgdata (at /home/hindsight/.pg0) are Docker named volumes. The macOS bind mount is case-insensitive, and the Python toolchain Hermes copies into installs/ contains both share/terminfo/a and share/terminfo/A — they collide and plugin installs fail. PostgreSQL on virtiofs is additionally slow and fsync-unsafe. Named volumes are ext4 inside the Docker VM, so both problems disappear. Override with HINDSIGHT_DATA_VOLUME=./data-hindsight if you want the database on the host anyway.

Services, Ports & Logins

Everything the stack exposes, and how to reach it

A make up brings up three containers. hermes waits for hindsight to report healthy before it starts, so a first boot takes a minute or two while Hindsight initialises its PostgreSQL.

Service Container Image What it is for
hermes hermes-agent built from docker/Dockerfile The agent. Runs gateway run, exposes an OpenAI-compatible API, and serves the Web UI on :9119 — s6-overlay supervises the gateway and the dashboard side by side in this one container.
omniroute hermes-agent-gtw ghcr.io/diegosouzapw/omniroute:latest AI gateway: one endpoint in front of many providers, with fallback, load balancing and token compression.
hindsight hermes-agent-hindsight ghcr.io/vectorize-io/hindsight:latest Self-hosted long-term memory: knowledge graph, entity resolution, multi-strategy retrieval. Bundles PostgreSQL + pgvector.

Ports & default credentials

URL What Default credentials Shortcut
http://localhost:9119 Hermes Web UI dashboard (served by the hermes container) admin / hermes-admin make webui
http://localhost:20128 OmniRoute dashboard + /v1 gateway password omniroute-admin make gtw-dashboard
http://localhost:8888 Hindsight REST API none by default make hindsight-health
http://localhost:9999 Hindsight memory explorer UI none by default make hindsight-ui
http://localhost:8642 Hermes OpenAI-compatible API server API_SERVER_KEY; off unless API_SERVER_ENABLED=true —
Change the passwords. DASHBOARD_USERNAME, DASHBOARD_PASSWORD and OMNIROUTE_INITIAL_PASSWORD all live in .env. The Hermes dashboard binds 0.0.0.0 inside the container, so basic auth is the only thing in front of it.

One Hermes container, two supervised processes

The official Hermes image is s6-overlay supervised. gateway run is redirected to the supervised service, which also starts a dashboard whenever HERMES_DASHBOARD is truthy (1, true, yes). So the agent and the Web UI are two supervised processes in one container — both get auto-restart on crash.

Confirm both processes came up
$ docker compose logs hermes | grep -i dashboard
s6-rc: info: service dashboard: starting
s6-rc: info: service dashboard successfully started
HERMES_DASHBOARD_READY port=9119
Why this is not two containers. An earlier version of this repo ran a second container off the same image and the same ./data bind mount. That meant two writers against the same SQLite/WAL files (state.db, kanban.db) and two gateway supervisors over one gateway.sock — exactly the conditions that corrupt shared gateway state. One container with two supervised processes is both the supported design and the safe one. Set HERMES_DASHBOARD=0 in .env for the agent without the Web UI.
The dashboard answers 302, and that is correct. A non-loopback bind engages the auth gate, so / redirects to /login?next=%2F, which serves 200 with the Sign in — Hermes Agent page. HERMES_DASHBOARD_INSECURE is accepted but ignored since the June 2026 hardening; a public dashboard always requires an auth provider — basic auth (which this compose file sets) or OAuth — and fails closed if neither is present.

Demo 5: OmniRoute — One Endpoint, Many Providers

Make the gateway serve a real model, then prove Hermes routes through it

Do this demo first. Nothing in the stack can call a model until OmniRoute has an upstream provider and a client API key. On a fresh install make verify correctly reports HTTP 401 Invalid API key — the shipped GTW_API_KEY=omniroute-local is a placeholder, not a working key.

Step 1: Open the gateway dashboard

Host Terminal
$ make gtw-dashboard
Opening OmniRoute Dashboard at http://localhost:20128...

Log in with omniroute-admin, or whatever you set as OMNIROUTE_INITIAL_PASSWORD in .env.

Step 2: Connect an upstream provider

Add a provider connection using your own account or API key — OpenAI, Anthropic, OpenRouter, Google and many more. This is the only place a real model credential needs to live.

Worth narrating while you are in the UI:

FeatureWhat to show
Fallback tiers Routing falls back across four tiers — subscription, API key, cheap, free — while any healthy target remains.
Resilience layers Provider circuit breakers, per-connection cooldowns, and per-model lockouts.
Routing strategies Around 20: round-robin, weighted, power-of-two-choices, least-used, headroom-based. Quota-Share splits one shared account's quota across pooled keys.
Token compression RTK and Caveman compression, advertised at roughly 15–95% token savings.

Step 3: Create a client key and hand it to the stack

Go to Dashboard → Endpoints, create an API key, and copy it. Then edit .env:

.env
# replace the placeholder with the key you just copied
GTW_API_KEY=<your-omniroute-key>
Host Terminal
$ make restart
Both Hermes and Hindsight read GTW_API_KEY, so this single edit fixes inference and Hindsight's entity extraction at once.

Step 4: Prove it from inside the Hermes container

Before — placeholder key
$ make omniroute-models
--- GET http://omniroute:20128/v1/models as seen BY HERMES ---
HTTP 401
{"error":{"message":"Invalid API key","type":"invalid_api_key","code":"invalid_api_key"}}

401 = OmniRoute does not recognise GTW_API_KEY ('omniroute-local').
OmniRoute requires a key that exists in ITS OWN database, even when
OMNIROUTE_REQUIRE_API_KEY=false. The default value is a placeholder.
After — real key + upstream provider
$ make omniroute-models
--- GET http://omniroute:20128/v1/models as seen BY HERMES ---
HTTP 200
{"object":"list","data":[{"id":"...","object":"model", ...}]}
OMNIROUTE_REQUIRE_API_KEY=false does not disable client-key checking on /v1. OmniRoute accepts only keys that exist in its own storage.sqlite (under ./data-gtw/). There is no way around creating one in the dashboard.

Step 5: Route Hermes through the gateway

Host Terminal
$ make provider-omniroute
✓ Set model.provider = custom in /opt/data/config.yaml
✓ Set model.base_url = http://omniroute:20128/v1 in /opt/data/config.yaml
Container hermes-agent  Started
Hermes now routes inference via OmniRoute (bearer token = GTW_API_KEY).

$ make provider-show
model.provider : custom
model.base_url : http://omniroute:20128/v1
model.default  : anthropic/claude-opus-4.6

$ make model   # pick a model OmniRoute actually serves

model.default must be a model your gateway can actually serve. A model name with no matching upstream fails at request time, not at config time — so the config looks perfectly healthy right up until the first message.

Step 6: Flip between gateway and direct

Host Terminal
$ make provider-omniroute  # through the gateway
$ make provider-direct     # straight to OpenRouter, bypassing it
$ make provider-show       # which am I on right now?
$ make gtw-logs            # watch the gateway handle live requests

provider-omniroute sets Hermes' model.provider to custom — Hermes' name for “any OpenAI-compatible endpoint” — and model.base_url to the service URL. The bearer token Hermes sends is resolved in this order:

Key resolution order for provider “custom”
model.api_key (config.yaml)  →  CUSTOM_API_KEY  →  OPENAI_API_KEY  →  OPENROUTER_API_KEY

docker-compose.yml sets CUSTOM_API_KEY=${GTW_API_KEY}, which is why putting the key in .env is sufficient — no secret ever needs to be written into config.yaml.

Demo 5b: Free Combos — A Working Stack With Zero Credentials

Real completions with no provider API key, and the hard limits that come with them

OmniRoute can serve real completions using built-in keyless (noauth) providers. That is what makes this course runnable for everyone. It also has limits you must know before building a demo on it. Everything below was measured on this stack, not assumed.

What a “combo” actually is

auto/* model IDs are routing chains, not models.

Model IDMeaning
autoZero-config routing across all connected targets (LKGP strategy). Does not use saved combos.
auto/<variant>A weight profile: coding, fast, cheap, offline, smart, lkgp, chaos.
auto/<category>:<tier>Category (coding, reasoning, vision, chat, multimodal) + tier (fast, cheap, reliable, free, pro).
my-combo / combo/my-comboA persisted combo you created (Settings → Combos, or POST /api/combos).

This gateway advertises exactly two free routing IDs: auto/best-free and auto/coding:free.

Tier filtering is FAIL-OPEN. If no connected model matches :free, OmniRoute falls back to the full pool. A :free model string is a preference, not a cost guarantee. Pair it with Settings → Routing → Hide paid models if you need a hard boundary.

Step 1: Build the browser-enabled gateway image (required)

The biggest keyless provider, cloudflare-playground, drives a real browser. The published image ships the playwright npm package but not Chromium, so every free request fails:

Before
Cloudflare Playground needs Playwright and its Chromium browser.
Install the browser runtime ... or use an OmniRoute
browser-enabled deployment. (HTTP 503)

No browser-enabled tag is published upstream (all 100 tags checked), so we add it in a thin derived layer.

Host Terminal
$ make omniroute-browser-build
# then in .env:
OMNIROUTE_IMAGE=omniroute-browser:local
$ docker compose up -d omniroute
$ docker exec hermes-agent-gtw ls /ms-playwright
chromium-1234  chromium_headless_shell-1234  ffmpeg-1011
One non-obvious detail inside that build: npx playwright install exits 127 in this image — the bundled playwright package declares bin → cli.js but the file is absent and there is no node_modules/.bin/playwright. docker/Dockerfile.omniroute calls node /app/node_modules/playwright-core/cli.js install --with-deps chromium instead.

Step 2: Mint a gateway client key (no browser needed)

Host Terminal
$ make omniroute-key
Logging in to http://localhost:20128 ...
A key named 'hermes-course' exists but its secret is masked (allowKeyReveal=false); minting a new one.
Creating API key 'hermes-course' ...
Wrote GTW_API_KEY to .env (value not printed; backup kept).

This logs into OmniRoute's own admin API with OMNIROUTE_INITIAL_PASSWORD, creates a key, verifies it against /v1/models, and writes it to .env.

The masked-key trap. GET /api/keys returns masked values when allowKeyReveal is false (the default) — a ~16-character prefix instead of the real ~35-character key. Anything read back from the listing will 401. That is why the script verifies before writing.

/v1/models lies about this. OmniRoute advertises "capabilities":{"tool_calling":true} on auto/* entries. That is combo-level metadata, not a promise the keyless upstream honours. Bottom line for the course

Free combos are excellent for proving the plumbing end to end, smoke tests and plain chat — at zero cost and zero signup. For the memory recall demo, or anything tool-using, connect a real provider in the dashboard (Demo 5) and set HINDSIGHT_MEMORY_MODE=hybrid. One upstream key makes the whole stack behave.

Memory Modes & the Privacy Trade-off

Three ways to run Hindsight, and what each one sends where

Set HINDSIGHT_MODE in .env, then re-run make hindsight-enable.

Mode Where memory lives Needs Use when
local_external (this stack's default) The hindsight container, on your machine The compose service You want a fully local demo you can open and inspect.
cloud Vectorize's hosted service HINDSIGHT_API_KEY + HINDSIGHT_API_URL=https://api.hindsight.vectorize.io You want zero ops and do not mind the data leaving.
local_embedded A daemon Hermes starts itself, inside the Hermes container Nothing — fetched with uvx, version-pinned, on first use You want no separate service and accept a cold start plus an idle timeout.
Read this out loud during the demo. The plugin's own disclosure, verbatim from hermes plugins info hindsight:

“Disclosure — in cloud mode (and local external) every turn's conversation, and every entry the agent adds or replaces in Hermes's built-in MEMORY/USER stores, is sent to api.hindsight.vectorize.io or the URL you configure, into every bank it writes to; local embedded mode starts a background Hindsight daemon (fetched with uvx, version-pinned, on first run when hindsight-api is not installed) and keeps its LLM settings in ~/.hindsight/profiles/<profile>.env; setup writes the keys you enter to the profile .env; repositories under folders you list in trusted_project_dirs may choose their bank with .hindsight/config.toml.”

So local_external is not automatically private. It is private because the URL you configured happens to be a container on your own machine. Point HINDSIGHT_API_URL at a remote host and every single turn goes there instead. Always check which one you are on before demoing with real data:

Hermes Doctor: Common Warnings & Step-by-Step Fixes

Understanding and resolving diagnostics in Docker and local environments

Running make status (or hermes doctor) scans credentials, SQLite integrity, security advisories, tool dependencies, and npm workspaces. Below is the breakdown and fix strategy for each reported diagnostic.

1. Missing API Keys

Tool providers need keys to enable search, vision, or web extract.

make setup-keys
2. NPM Vulnerabilities

Baked in root, web, and ui-tui workspaces. Requires upstream lockfile bump.

3. Profile Token Collisions

Cloning duplicates Telegram tokens. Gateway stops duplicate adapters.

Issue 1: "Run 'hermes setup' to configure missing API keys for full tool access"

Hermes tools (such as web search, vision, firecrawl web extract, or image gen) check for provider configurations or environment tokens. When running in Docker, you can configure them interactively or via .env.

Interactive Key Configuration

Issues 2, 3 & 4: NPM Vulnerabilities in root, web, and ui-tui Workspaces

Doctor Message: "Root npm package has 1 npm vulnerability; wait for an upstream lockfile fix, then update your installation (Docker: pull a rebuilt image; recreating the same image restores the same dependencies)"

Why this happens and why manual npm audit fix inside the container is not the solution:

  • In Hermes Docker images, frontend assets (ui-tui, web, and root CLI) are assembled during Docker image build time from the upstream Nous Research git repository lockfile (package-lock.json).
  • The internal filesystem at /opt/hermes is mounted read-only or sealed to ensure runtime integrity. Any ad-hoc changes inside the container get overwritten on container reboot.
  • Resolution Strategy: As stated by Nous Research, wait for the upstream lockfile bump in the official repository. Once merged, pull the freshly built image with a single command:
Terminal
$ make update-image

✔ Container hermes-agent  Recreated
✔ Container hermes-agent  Started

Issue 5: Duplicate Bot Credentials Across Profiles

Doctor Warning: "Duplicate platform credential across profiles: Profiles 'asimov-approver' and 'marcio-pm' both hold the same telegram credential (TELEGRAM_BOT_TOKEN)... one platform token can serve only one gateway."

When running hermes profile create <name> --clone, Hermes copies .env verbatim into the new profile's directory. Because Telegram only allows one connection per bot token at a time, the second adapter is parked.

Automated Fix in our Makefile:

Running make profile-create NAME=mybot CLONE=1 now automatically runs config unset TELEGRAM_BOT_TOKEN and config unset API_SERVER_ENABLED on the new profile immediately after creation.

Fixing Existing Profiles Manually

Issue 6: Gateway Inaccessible: unsafe_control_permissions (gateway.sock has mode 0755, expected 0600)

Error message: "Error: Gateway inaccessible: unsafe_control_permissions (/opt/data/gateway.sock has mode 0755, expected 0600; chmod 600 /opt/data/gateway.sock)"

Why this happens on macOS:

  • When Hermes starts the gateway process inside the container, it binds a Unix domain control socket at /opt/data/gateway.sock.
  • Because /opt/data is bind-mounted directly to your host directory ./data through Docker Desktop's virtiofs / osxfs filesystem bridge, macOS file sharing defaults to 0755 (read/execute for group/others).
  • For security (to prevent local privilege escalation and rogue cross-user control), Hermes strictly enforces mode 0600 (read/write only by owner) on gateway.sock. When the CLI verifies the socket, it refuses to connect if group or other bits are set.

The Fix:

The permission bits must be restricted to 0600 on the host filesystem. The updated Makefile now does this automatically before every make chat, make setup-keys, and make status invocation.

Quick Fix Terminal Command
$ chmod 600 ./data/gateway.sock
# Or run the built-in target:
$ make fix-permissions
$ make chat

Plugin install fails: File exists: .../share/terminfo/A

Error Output

[('/opt/hermes/tools/python-.../share/terminfo/q',
  '/opt/data/installs/.../share/terminfo/q',

ValidationError ... _ConstrainedConsolidationBatchResponse

make hindsight-logs
ValidationError: 1 validation error for _ConstrainedConsolidationBatchResponse
  Input should be a valid dictionary or instance of
  _ConstrainedConsolidationBatchResponse

   'category': 'monitoring'}], input_type=list]

What it is. Consolidation asks the LLM for a strict JSON object {"creates":[...],"updates":[...],"deletes":[...]} (consolidator.py:852). The model returned a bare list, so Pydantic rejects the whole batch. The entries carry fact_id/category, which are not fields of any action model — those key on observation_id (_UpdateAction, _DeleteAction) or carry no id at all (_CreateAction). The model is parroting the input facts back instead of emitting actions.

Root cause: MODEL-specific, not provider-wide. auto/best-free routes to glm-5.2, which parrots input. Other keyless models on the same gateway return a correct object.

HINDSIGHT_API_CONSOLIDATION_LLM_REASONING_EFFORT=low
HINDSIGHT_API_CONSOLIDATION_LLM_BATCH_SIZE=2

Pin a specific model, not an auto/* combo — a combo can reselect glm-5.2 on any request, so the error would come back intermittently. Verify with make hindsight-consolidate.

Pinning a model is necessary but NOT sufficient. cfp/deepseek-ai/deepseek-v4-flash-0731 passes a toy json_object probe, yet on Hindsight's real consolidation prompt it still parrots input — 28 further ValidationErrors, created=0 updated=0 failed=1 on every batch. The toy probe was not representative of a large prompt carrying the full creates/updates/deletes schema with enum-constrained source_fact_ids. The pin fixes OutputTooLongError, not the shape error.

The actual fix: tolerant parsing. A locally built image adds a narrow model_validator(mode="before") to _ConsolidationBatchResponse — the base class, so _ConstrainedConsolidationBatchResponse inherits it — which coerces a bare list.

HINDSIGHT_IMAGE=hindsight-patched

A bare id is never mapped onto observation_id. In parroted output id is a fact id, and treating it as an observation id would rewrite the wrong record.

This patches vendor code and is pinned to one upstream version. docker/hindsight-tolerant-batch.patch.py asserts every anchor (the pydantic import line and the exact class body) and aborts the build if upstream changed shape, so an image bump can never silently yield an unpatched image. The Dockerfile then runs a five-case self-test inside the real venv (patch self-test OK), so a broken patch fails at build time rather than at the first consolidation round. On a Hindsight image bump, re-check that script and rebuild. To go back to stock: HINDSIGHT_IMAGE=ghcr.io/vectorize-io/hindsight, HINDSIGHT_VERSION=latest.
Trap 1: HINDSIGHT_API_ENABLE_AUTO_CONSOLIDATION=false does NOT stop consolidation. It only suppresses the inline post-retain trigger; a background worker poller keeps claiming queued consolidation tasks (claimed 1 tasks (1 consolidation)). Measured with the flag false in the running container: 30 consolidation runs and 24 ValidationErrors. Disabling it is not a fix, and not even a reliable workaround.
Trap 2: a reasoning-heavy model swaps one error for another. cfp/openai/gpt-oss-120b emits the right shape but spends its whole output budget thinking and gets truncated: non-retryable OutputTooLongError: LLM output exceeded token limits (scope=consolidation). Raising the cap does not help — DEFAULT_CONSOLIDATION_MAX_COMPLETION_TOKENS is None, so Hindsight is not the one capping it; the upstream playground is. Use a low-reasoning flash model and keep the batch small.

Why HINDSIGHT_API_LLM_STRICT_SCHEMA_CONSOLIDATION=true does not help: strict mode asks the provider for its strongest schema mode, and a provider that ignores response_format has none. DEFAULT_LLM_STRICT_SCHEMA is False, so the schema is only requested, never grammar-enforced.

Why no retry rescues it: ValidationError is classified FAIL_FAST (consolidator.py:3621). Consolidation pins temperature 0.0 and rebuilds a byte-identical payload, so re-sending asks a greedy decoder the same question. The caller bisects instead — which helps an oversized batch, never a systematic shape error.

Consolidation never runs and logs nothing — a stale worker lease

The most confusing of the three, because nothing errors. Consolidation simply never happens.

The background worker claims queued tasks under a lease keyed to its worker id. Recreating or replacing the container — docker compose up -d after an .env change, --force-recreate, an image bump — kills that worker while the lease still points at it. A new worker will not steal the task:

An orphaned task
global: pending=1 (queried=1/1 schemas: default) | others: 9454be36ad5d:1 | my_active: none
[PENDING_BREAKDOWN] consolidation: total=1 payload_null=0 retry_blocked=0 assigned=0

pending=1, but others: names a worker that no longer exists while the live worker is idle. It sits like that indefinitely.

The trap inside the trap: POSTing /consolidate again returns {"operation_id":"b6b1eb1c-...","deduplicated":true} — it folds into the same stuck task. Retrying looks like it worked and does nothing.

$ make hindsight-unstick      # restart runs the startup reconcile
$ make hindsight-consolidate

The free keyless pool vanishes mid-session

The single most important operational caveat in this stack. The keyless pool is ephemeral. Observed in one session, eleven minutes apart:

make gtw-logs
01:24:04  AUTH  Using cloudflare-playground account: ***...     -> status=success
01:35:31  AUTH  No active credentials for provider: cloudflare-playground

The anonymous account expired or hit its quota, and cloudflare-playground dropped out of the pool entirely:

make free-combos, before and after
before:  candidates: 21 | by provider: {'cloudflare-playground': 20, 'uncloseai': 1}
after:   candidates: 1  | by provider: {'openrouter': 1}

Everything downstream fails at once — Hermes turns, Hindsight retain, and consolidation — all with 401 provider_not_configured. Restarting OmniRoute does not recover it (verified: 12 polls over 3 minutes, still 1 candidate).

OmniRoute's own docs warn about this: “keyless availability is not guaranteed” and “Providers can rate-limit, change models, or go offline.” Treat free keyless capacity as a demo convenience, never as a dependency. If the course must run to a schedule, connect one real provider in the dashboard — the pool then falls back to it instead of going to zero.

Not an auth failure and not a broken stack. The probe has a ~10 s budget, while the free keyless provider is browser-driven and routinely takes 30–150 s per call. The same stack returned connected at 4672 ms minutes earlier — latency simply fluctuates.

Use the model-independent round trip instead, which is the real proof: make hindsight-roundtrip.
